# localcode evals

One suite, two kinds of eval, three commands. The no-model parts (Checks and the task
graders' oracle verification) run in CI on every PR; the model runs are local.

| Command | Kind | Needs a model | Takes |
| --- | --- | --- | --- |
| `python -m pytest evals/checks -q` | Checks | no | 40 s |
| `python3 evals/verify_oracles.py` | Task graders | no | 20 s |
| `python3 evals/run_tasks.py --repo <checkout> --model <alias> [--set regression] [--trials 3]` | Tasks | yes | minutes to hours |
| `python3 evals/gate.py runs/<baseline>/results.jsonl runs/<candidate>/results.jsonl` | gate | no | instant |

`<checkout>` is a localcode checkout with `src/localcode/bin/localcode-ui` (the runtime
under test); localcode must be importable by `LOCALCODE_PY`, `<checkout>/.venv/bin/python`,
or the interpreter running the script. `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS=1` is set for
the Checks so a developer's own skill folders cannot change the measured prompt. Results land in `evals/runs/<date>-<label>-<model>/results.jsonl` (gitignored),
one row per trial: task, quality, component, purpose, model, pass, notes, steps,
tool_calls, wall_s, reread_tokens per turn, binary_sha.

- `checks/` — canned servers drive the real UI runtime headlessly; asserts the plumbing
  (identical system prompt across a session, tool schemas, budgets, no runtime errors,
  side requests on the last slot, model name). A mutation test proves the prefix check
  can fail.
- `tasks/` — twenty tasks in Harbor layout, generated by `gen_tasks.py`. Edit the
  generator, not the files. `tasks/README.md` documents the `.eval/` contract graders
  rely on.
- `run_tasks.py` — one isolated supervisor and model per run (throwaway HOME, spare
  ports, single slot); per trial a fresh git workspace, one `localcode-ui run` per
  turn, the `.eval/` artefacts, then the hidden grader.
- `gate.py` — paired per-task difference against a baseline; blocks only when the mean
  drop exceeds max(5 points, 2 SE) and at least one task went all-pass to all-fail.

Taxonomy: every task is tagged with a quality (capability, reliability, safety_scope,
efficiency, fidelity), a component (model, harness, runtime, ui) and a purpose
(regression, tracking). Regression tasks are expected near 100% and gate a release;
tracking tasks show where to work next.

## A/B on one model

Any launcher setting with an environment override can be compared with the gate. Example,
the speculative drafter on and off for the same model and quant:

```
LOCALCODE_LLAMA_CPP_MTP_DRAFT=0 python3 evals/run_tasks.py --repo . --model <alias> --trials 2 --label nodraft
python3 evals/run_tasks.py --repo . --model <alias> --trials 2 --label draft
python3 evals/gate.py evals/runs/*-nodraft-*/results.jsonl evals/runs/*-draft-*/results.jsonl
```

`nightly.sh <checkout> [alias ...]` strings the whole thing together for a machine that has
the models downloaded, and refuses to run while an interactive localcode session holds the
supervisor port.
