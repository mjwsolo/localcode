Release process

Bugs reached users because testing ran from the repository, on one big Mac, with the developer’s own settings. Users run the published package from a fresh install on 16 to 128 GB Macs. A release therefore goes out as a release candidate first, and every check runs against that candidate installed from PyPI, in a fresh virtual environment with a fresh HOME.

Cutting a release

Section titled “Cutting a release”

On the Mac that has the models, from main (or a release/* branch) with a clean tree that matches origin, and with CHANGELOG.md holding a ## 0.5.41 or ## Unreleased section:

It refuses to start if the tree is dirty, the branch is not main or release/* or is not up to date with origin, another llama-server is running, the changelog has no notes, or v0.5.41 exists. Then:

  1. Candidate. Picks the next free 0.5.41rcN from the tags (scripts/release_candidate.sh), commits the bump on release/<version>, opens a PR to main (main is protected, admins included, and publish.yml only releases commits on main), waits for its checks, merges it with a merge commit, and tags that merge commit v0.5.41rcN. This is the only push before promotion. publish.yml publishes it to PyPI as a pre-release and creates a GitHub release marked --prerelease. A candidate is never the default install: PEP 440 pre-releases are skipped by pip install localcode and uv tool install localcode. The release notes use the rcN, the final version or the Unreleased section of the changelog, so a candidate needs no heading of its own.
  2. Wait for PyPI to serve it.
  3. Install the candidate into a fresh venv. Everything below tests that install, each in a temporary HOME, XDG and LOCALCODE_HOME. The real models directory is passed explicitly, and the developer’s LOCALCODE_* variables, config, UI preferences and sessions cannot change a result.
    • localcode doctor
    • the terminal snapshot suite against the installed localcode-ui and Python modules: scripts/ui_e2e.sh --installed <venv python>
    • the local model gate: verify_models.py --installed --strict --publish-status posts the commit status local model gate on the candidate commit
    • the release eval, scripts/release_eval.sh, posts release eval
  4. Promote. When both statuses are green, the script dispatches .github/workflows/release.yml with the candidate. That run re-reads both statuses on the candidate commit, runs the installed-package checks on a hosted macOS 15 runner (fresh venv and HOME, localcode doctor, the snapshot suite in installed mode; logs and diffs are uploaded), and then pushes the tag v0.5.41 pointing at the same commit as v0.5.41rcN, through the git refs API, and starts publish.yml on that tag. Promotion creates no commit and no pull request, so branch protection on main is not involved and the “local model gate” status stays valid for exactly what is released. When publish.yml sees a final tag on a commit whose version is 0.5.41rcN (and that commit carries the tag v0.5.41rcN), it sets 0.5.41 in pyproject.toml and src/localcode/__init__.py inside its build job only, builds and publishes. The changelog may use a ## 0.5.41, ## 0.5.41rcN or ## Unreleased heading for the release notes. A final tag on any other commit is refused. Ordinary version-bump releases work as before.
  5. Post-publish checks run automatically in publish.yml on macOS 15: the exact version is installed with pip and uv (including an upgrade from 0.4.9), and with pip into a fresh venv, where localcode doctor and the snapshot suite run against the installed package. release.sh waits for them.

If any check fails, the script stops before promotion, prints which check failed and where its log is, and nothing is promoted. The candidate stays published as a pre-release; fix the cause and run the script again, which uses the next rcN.

main carries the 0.5.41rcN version string until the next release bumps it. The bundled localcode-ui binary is committed, not rebuilt by publish.yml, so its footer shows the version it was last built with (as for every release); rebuild it with scripts/build_ui_binary.sh in a normal change if the footer must match.

Pushing a v*rc* tag by hand also starts release.yml, which publishes the candidate and runs the hosted checks, but never promotes: only the dispatch that release.sh sends after both local statuses are green can.

Using a candidate yourself

Section titled “Using a candidate yourself”

An exact pin selects a pre-release without any flag in pip; uv needs --prerelease allow. To go back to the stable release: uv tool install --reinstall localcode (or pip install --upgrade localcode).

The release eval

Section titled “The release eval”

scripts/release_eval.sh --model <name> [--candidate-venv DIR] runs six fixed Harness-Bench tasks (002-monorepo-affected-build, 010-layered-config-resolution, 035-workspace-dependency-resolution, 092-bounded-cache-eviction-repair, 089-file-watcher-atomic-save-repair, 120-http-cookie-jar-policy-repair) twice with the same local model: on the candidate, then on the previous release installed from PyPI into a temporary venv. Each run has a fresh HOME. It prints mean score, tasks passed and total wall time for both and exits 1 if the mean score dropped by more than 0.05 or the run was more than 25% slower. It refuses to start while any llama-server is running (GPU contention ruins timings) and never downloads models; the Harness-Bench data must already be in evals/data (see evals/README.md). --dry-run prints the plan.

Why the model checks run on the Mac and not in CI

Section titled “Why the model checks run on the Mac and not in CI”

Hosted runners have about 7 GB of RAM and no models. The gate therefore runs on the owner’s Mac and records its result as a commit status, the same pattern the Model promotion gate uses for pull requests. No self-hosted runner is registered and none of the workflows can use one.

What the workflows guard

Section titled “What the workflows guard”

release.yml has no pull_request trigger. Its jobs run only when github.repository_owner == github.actor and the repository is not a fork. It uses the workflow token only: tags and the release commit are pushed by the workflow token only (it creates one tag ref), and because refs created with that token do not start other workflows, the promote job starts publish.yml explicitly with workflow_dispatch on the new tag. release.sh waits for the publish.yml run whose ref is v0.5.41 and whose head is the candidate commit.
